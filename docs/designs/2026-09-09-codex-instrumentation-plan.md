## Measurement boundaries

Here, **measured** means two timestamps in the same process around an identified operation. **Bounded** means observable events bracket an interval without exposing its internal boundaries. **Unobservable** means neither profiler process has the necessary event or clock anchor.

# 2. Websocket measurement methodology

## Stack and measurement scope

Use **FastAPI + uvicorn + websockets**, with stdlib JSON, clocks, statistics, compression, and file handling.

The existing libraries supply connection management, Ping/Pong, buffering, compression negotiation, and supported socket injection. Building a WebSocket stack would add measurement bias and maintenance work. A raw TCP comparison would also change the protocol and require another serving path; defer it.

Async execution is warranted here: fixed-tick scheduling, simultaneous slot connections, and control-frame handling must continue while another connection waits. Keep computation and artifact helpers synchronous; run blocking artifact I/O in a thread while the server remains responsive.

Explicitly select the event loop and WebSocket implementation. Record dependency versions and resolved settings in every replay; uvicorn’s automatic choices otherwise make comparisons ambiguous. [Uvicorn implementation settings](https://uvicorn.dev/settings/)

## Clock rules

- Use **`time.monotonic_ns()` for every duration and local ordering decision**.
- Use **`time.time_ns()` only for wall-clock alignment and four-timestamp offset estimation**.
- Use **`time.thread_time_ns()` for the busy player’s CPU budget**; use process CPU counters for whole-process resource samples.
- Never directly subtract game and player monotonic timestamps.
- At startup, shutdown, and every ten seconds, capture a bracketed anchor: monotonic-before, wall time, monotonic-after. Retain the bracket width.
- Detect changes in wall-minus-monotonic offset. Split alignment into segments after a clock discontinuity.
- Store nanosecond timestamps as decimal strings in JSON artifacts, preserving integer precision in browser clients. Store aggregate durations as seconds.

Monotonic clock origins are unspecified; process CPU time excludes sleep. Those properties are why local duration and cross-host alignment use different clocks. [Python clock documentation](https://docs.python.org/3.12/library/time.html)

## Message shapes

All messages carry `protocol_version`, `run_id`, and a unique message/sequence identifier. Slot identity comes from the authenticated connection; a body cannot override it.

Illustrative game observation:

```json
{
  "type": "observation",
  "protocol_version": 1,
  "run_id": "<game-generated UUID>",
  "seq": 42,
  "tick": 42,
  "phase": "measure",
  "cell_id": "json-16384",
  "payload": "<deterministic generated content>"
}
```

Illustrative action:

```json
{
  "type": "action",
  "protocol_version": 1,
  "run_id": "<same UUID>",
  "reply_to": 42,
  "tick": 42,
  "action": "noop",
  "completed_timings": [
    {
      "seq": 41,
      "receive_mono_ns": "<integer>",
      "decode_end_mono_ns": "<integer>",
      "think_begin_mono_ns": "<integer>",
      "think_end_mono_ns": "<integer>",
      "encode_begin_mono_ns": "<integer>",
      "encode_end_mono_ns": "<integer>",
      "send_begin_mono_ns": "<integer>",
      "send_end_mono_ns": "<integer>"
    }
  ]
}
```

Other message types:

| Message | Purpose |
|---|---|
| `hello` | Player implementation/version, startup records, connection-attempt records, available resource counters |
| `configure` / `ready` | Establish workload settings and explicit protocol readiness |
| `clock_probe` / `clock_reply` / `clock_report` | Four-timestamp exchange, with completed timestamps reported afterward |
| `timings_flush` / `timings_ack` | Transfer the remaining completed timing records |
| `finish_measurement` | Stop workload, drain outstanding replies, prepare player artifact |
| `artifact_done` | Publication outcome, bytes, duration, and completeness |
| `final` | Close the session and exit cleanly |

**Resolve timing self-reference with delayed reports.** Action 42 carries the completed timing for action 41. The current action’s final encoding time and send timestamp become known only after its bytes exist. Flush the last record explicitly. Bound report batches and record their actual encoded size.

The game can compute RTT immediately. Processing and residual values become available when the matching completed record arrives. Missing reports produce null decomposition fields, never assumed zero processing.

## Round-trip and processing boundaries

For each observation/action pair:

| Timestamp | Boundary |
|---|---|
| `g0` | Game begins observation JSON encoding |
| `g1` | Game calls send with the encoded observation |
| `g2` | Game send await returns |
| `p0` | Player receive returns a complete application message |
| `p1` | Player JSON decode completes |
| `p2a`, `p2b` | Player think begins/ends |
| `p3a`, `p3b` | Player action JSON encoding begins/ends |
| `p4` | Player calls send with encoded action |
| `p5` | Player send await returns |
| `g3` | Game receive returns a complete action message |
| `g4` | Game decodes and validates the action |

Compute:

```text
websocket.application_rtt       = g3 - g1
player.turn.duration            = g4 - g1
player.processing.duration      = p4 - p0
websocket.transport_residual    = (g3 - g1) - (p4 - p0)
observation_to_usable_action    = g4 - g0
game.websocket.send_await       = g2 - g1
player.websocket.send_await     = p5 - p4
```

Also retain decode, think, encode, and the remaining player overhead separately.

**`transport_residual` is not pure network transit.** It includes socket buffering, WebSocket framing, library work outside the player-processing boundary, and scheduling before application receive returns. Negative values are invalid samples requiring inspection; retain and flag them rather than silently clamping.

Send-await duration overlaps the round trip and can include suspension after bytes have already progressed. Do not subtract it again or sum it with RTT as exclusive work.

The proposed `player.turn.duration` includes receipt and validation of a usable response. That is the hosted analogue of arena’s message delivery through returned responses; it is not identical to arena’s in-process execution cost. [pump.py:143](/Users/jamesboggs/coding/metta/app_backend/src/metta/app_backend/arena_runner/pump.py:143)

## Four-timestamp offset estimation

Use small dedicated probes:

- `T1`: game wall timestamp immediately before sending a prepared probe.
- `T2`: player wall timestamp immediately after receive.
- `T3`: player wall timestamp immediately before sending a prepared reply.
- `T4`: game wall timestamp immediately after receiving the reply.

Store corresponding monotonic timestamps. A later `clock_report` returns `T2` and `T3`, avoiding timestamp-serialization circularity.

For player clock minus game clock:

```text
offset_estimate = ((T2 - T1) + (T3 - T4)) / 2
delay_estimate  = (T4 - T1) - (T3 - T2)
```

These are the standard NTP four-timestamp equations. [RFC 5905, §8](https://www.rfc-editor.org/rfc/rfc5905.html#section-8)

Under a stable offset and nonnegative directional delays:

```text
offset_lower = T3 - T4
offset_upper = T2 - T1
```

Widen the interval for timestamp-capture uncertainty and estimated drift. The midpoint assumes symmetric delays; the data cannot establish that symmetry.

Sampling:

- Eight probes per slot after readiness, outside the measured workload.
- One probe every ten seconds during long episodes, staggered by slot.
- Eight probes per slot after measurement.
- Preserve every probe. Use the minimum-delay valid probe in each local window as the representative estimate.
- Flag workload samples overlapping probes so they can be compared separately.

Directional estimates are then:

```text
game_to_player ≈ player_receive_wall - game_send_wall - offset_estimate
player_to_game ≈ game_receive_wall - player_send_wall + offset_estimate
```

Present ranges as well as estimates. Reject directional interpretation across wall-clock jumps or inconsistent offset intervals. “Skew” should mean offset drift over time, not a single offset estimate.

## DNS, TCP, and handshake

Use the connection’s actual socket:

1. Time `getaddrinfo` for the Service hostname.
2. Time TCP connection attempts to its returned addresses.
3. Give the connected socket to the library through its documented `sock=` argument.
4. Measure library adoption plus HTTP WebSocket upgrade until connect returns.

Preserve the original URI’s Host and `/player?slot&token` target. Set `proxy=None` for this direct Service experiment. Record attempts, address family, retry waits, and total startup duration. Do not perform a separate DNS “test” before the actual connection: that would warm the lookup.

This deliberately makes socket setup explicit. Validate it against a control using ordinary `websockets.connect` in separate episodes before interpreting startup differences. The supported socket API and default proxy behavior are documented. [websockets client API](https://websockets.readthedocs.io/en/15.0.1/reference/asyncio/client.html)

Call the result **player-process DNS/TCP setup**, not “cold Service startup.” The init container has already exercised that path.

## Payload size, JSON, and backpressure

Use target payload sizes **1 KiB, 16 KiB, 256 KiB, and 2 MiB**, recording actual UTF-8 message bytes separately from the target and envelope overhead.

Default workload:

- Large observation, small action.
- Deterministic structured JSON content generated before the measured phase.
- Fresh serialization of the complete observation on every send.
- No payload bodies retained in traces; retain generator seed, shape, target size, and actual byte counts.
- Compression disabled explicitly at both endpoints.
- A separate compression comparison uses the same corpus and fresh connections. Compression can substantially change both bytes and CPU cost. [websockets compression documentation](https://websockets.readthedocs.io/en/15.0.1/topics/compression.html)

Measure encoding explicitly with `json.dumps`, then send the resulting text. Measure receive separately from `json.loads`. Paintarena’s `send_json` and `iter_json` combine these stages. [server.py:237](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/examples/paintarena/game/server.py:237), [server.py:297](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/examples/paintarena/game/server.py:297)

A small adapter comparison should also time the ordinary `send_json` call end to end, using otherwise identical episodes. Its await duration includes serialization and sending; call it `game.websocket.send_json_call_s`, not backpressure time.

For a JSON-versus-bytes control, use prebuilt binary payloads through the same WebSocket connection, with a small fixed correlation header. This measures the effect of removing JSON work. It does **not** isolate all websockets-library overhead.

## Fan-out and scheduling

For fixed-tick mode, use one receiver and one sender per slot. Give each sender one pending-observation position:

- Tick processing never awaits a slow slot’s send.
- A newer observation replaces an older unsent observation.
- Count replaced observations as `observation_dropped_before_send`.
- Record enqueue, send-start, send-end, send order, and queue residence.
- Allow only one active send per connection.

This bounded queue follows established per-client broadcast patterns. It prevents an unbounded backlog from becoming the benchmark’s dominant behavior. [websockets broadcasting guidance](https://websockets.readthedocs.io/en/15.0.1/topics/broadcast.html)

Compare **2, 4, 8, and 16 slots**, holding payload, pacing, policies, and instrumentation constant. Rotate enqueue order deterministically. Report the first-to-last send-start spread and worst-slot latency, alongside pooled values.

## Fixed-tick and blocking semantics

**Fixed-tick mode**

- Schedule tick `t` against an absolute monotonic target: `origin + t × step_seconds`.
- Record both scheduled and actual start.
- Observation `t` requests an action for the next update.
- At actual tick `t+1`, consume a valid action for `t` if ready; otherwise apply noop.
- Record late replies, but never apply them to a later state.
- Preserve overdue ticks and their scheduling lag; yielding between overdue iterations keeps socket tasks runnable. Record catch-up behavior explicitly.

For each action, retain:

- `arrival_late_ticks`: number of actual tick boundaries crossed since observation tick.
- `action_ready_late_ticks`: the same using decode/validation completion.
- `scheduled_deadline_lateness_ns`.
- `applied`, `late_discarded`, `duplicate`, or `invalid`.

Use histogram buckets **0, 1, 2, 3, 4, 5+**, plus separate missing, unsent, and unanswered counts. A delayed game clock can make actions appear timely against actual boundaries; scheduled-deadline lateness exposes that.

Test `step_seconds` **0.02**, **1/24**, and **0.05**.

**Blocking mode**

Run round-robin decisions: send one slot an observation, await its usable action or deadline, apply the action, then advance. Record each decision’s wait and timeout. Do not insert fixed-tick sleeps.

## Sampling and tails

- Retain every workload sample in profiling episodes.
- Default: 100 warmup ticks followed by 1,000 measured ticks.
- Keep first-observation and warmup distributions separately.
- Compute empirical nearest-rank **p50/p90/p99/max**, plus count, sum, and timeout/loss counts.
- Partition by slot, payload cell, codec, mode, and phase.
- Never average percentiles or pool payload cells into one headline latency.
- Preserve unanswered observations as censored samples, with elapsed wait at termination.
- Report a per-second timeline plus the full raw sequence.
- Use at least ten hosted episodes per comparison, with interleaved variant order and rotated policies. Quantify between-episode variation separately.

A 1,000-sample p99 describes roughly the top ten observations; it is not a stable estimate of rare production events.

For cgroup v2, resolve the process’s own cgroup and read available:

- `cpu.max`: quota and period.
- `memory.current`, `memory.peak`, `memory.max`, `memory.events`.
- `cpu.pressure`, when present, as supplementary evidence.

Record availability and deltas. Missing counters are **unknown**, not zero. Cgroup throttling is not a per-turn measurement and cannot be subtracted from latency. Ancestor limits may also complicate attribution. [Linux cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html)

**Cut from the initial implementation:** packet capture, eBPF, kernel socket timestamping, per-function profiling, tracemalloc, a raw TCP server, custom WebSocket framing, and new telemetry exporters. They add privileges, perturbation, or dependencies without first resolving the larger application-level ambiguities.

Calibrate recorder overhead before warmup. Run matched low-instrumentation controls before declaring the profiler trustworthy. Set an initial acceptance target of less than **5% change in baseline median turn latency**, while publishing absolute overhead and tail differences. Do not “correct” individual samples by subtracting average recorder cost.

## Publication order and the self-measurement limit

Use an explicit end-of-measurement barrier:

1. Stop generating observations; drain outstanding replies to a bounded deadline.
2. Flush completed player timing records to the game.
3. Players prepare and publish their ZIPs.
4. Players send `artifact_done`, including publication duration and outcome.
5. Game records those reports and permits players to exit.
6. Game prepares and atomically publishes replay.
7. Game includes replay preparation/publication timing in results, then atomically publishes results.
8. Game prints results-publication timing and its last lifecycle markers.

Player publication may replace an earlier checkpoint, but missing artifacts must not masquerade as complete measurements. The platform does not wait indefinitely for them and does not fail an otherwise successful episode solely because they are absent. [PLAYER.md:44](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/docs/roles/PLAYER.md:44)

Three unavoidable limits:

- A player ZIP cannot contain the completed duration of its own upload. Send that duration to the game and logs.
- Replay cannot contain its own completed publication duration. Put that duration in results and logs.
- Results cannot contain its own completed publication duration. Put that duration in logs; collection of the very last log line is best-effort.

Do not repeatedly overwrite final artifacts to chase these self-references.

For file URIs, write a temporary sibling and rename atomically. The worker checks artifact existence, so direct writes risk exposing a partial file. [kubernetes_runner.py:1345](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/runner/kubernetes_runner.py:1345)

For HTTP URIs, time the supplied endpoint request. Player artifact requests can pass through a worker-hosted forwarding server; its response includes forwarding work, but the player cannot split those components. [kubernetes_runner.py:291](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/runner/kubernetes_runner.py:291), [kubernetes_runner.py:1289](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/runner/kubernetes_runner.py:1289)

# 6. Player policies

Bundle three policy commands sharing the same connection, recorder, and artifact implementation.

| Policy | Behavior | Configuration |
|---|---|---|
| **Echo** | Decode observation, produce noop, encode/send action, return completed timing records | No artificial processing |
| **Busy** | Same protocol, with a deterministic arithmetic loop consuming a target amount of thread CPU per action | Command argument `--think-cpu-ms`; initially compare 1, 5, and 20 ms |
| **Slow-start** | Record startup, then sleep before the first connection attempt | Command argument `--connect-delay-seconds`; default zero |

Use command arguments rather than adding environment variables or worker behavior.

Every policy records:

- Earliest Python marker, imports, environment-read duration.
- Actual DNS/TCP/handshake attempts, failures, and retry waits.
- First observation and first action.
- Per-message decode, think, encode, send, and processing duration.
- Event-loop lag, clock probes, CPU/memory availability.
- Artifact preparation, compression, publication, and shutdown.

**Busy must target CPU time, not elapsed time.** A wall-clock busy loop would perform less computation when throttled, concealing the effect under investigation. Report actual CPU consumed and elapsed processing time separately.

**Slow-start belongs outside certification.** Compare modest delays first. The game’s timeout and worker’s pod-start deadline begin at different points; a running player that delays its WebSocket connection is not equivalent to a pod that never starts. The worker distinguishes those cases. [kubernetes_runner.py:834](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/runner/kubernetes_runner.py:834), [kubernetes_runner.py:1411](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/runner/kubernetes_runner.py:1411)

For protocol Ping RTT, each player sends a uniquely identified Ping once per second, staggered by slot, and records the matching Pong latency. Use a separate diagnostic deadline that records missing Pongs without closing the connection. FastAPI’s application messages are not protocol Pings; let the underlying WebSocket implementation answer control frames. The library exposes the matching Pong future directly. [websockets Ping API](https://websockets.readthedocs.io/en/15.0.1/reference/asyncio/client.html#websockets.asyncio.client.ClientConnection.ping)

Startup failure evidence may exist only in logs or an optional player artifact if the player never reaches the game. Report that completeness limit explicitly.

# 7. Risks and pitfalls

## Contract and lifecycle

- **Keep `ping_timeout=None` on every bundled player.** Preserve keepalive traffic; distinguish its control RTT from application RTT. Configure the profiler server’s timeout behavior explicitly so the busy policy does not accidentally turn a timing experiment into a disconnect experiment. [PLAYER.md:31](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/docs/roles/PLAYER.md:31)
- **Raise both endpoint message limits.** The client’s 1 MiB default is a limit on incoming **messages**, not simply individual frames. Use an explicit 4 MiB limit initially, including envelope overhead, and bounded receive queues. [websockets client limits](https://websockets.readthedocs.io/en/15.0.1/reference/asyncio/client.html)
- **Serve all required surfaces:** `/healthz`, `/client/player`, `/player`, `/client/global`, `/global`; plus `/client/replay` and `/replay` when using the proposed container replay mode. Answer protocol Pings. [GAME.md:36](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/docs/roles/GAME.md:36)
- **Reject invalid, missing, out-of-range, or duplicate slot credentials before treating a connection as a player.** Contract probes must not increment ready-slot counts. Paintarena’s token check is the starting pattern. [server.py:219](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/examples/paintarena/game/server.py:219)
- **Send a small immediate global snapshot**, identifying `stage: "lobby"`, then low-rate progress. Do not send multi-MiB workload frames to the worker’s viewer unless that is a separate experiment. The worker can hold the connection without consuming application messages during startup. [runner.py:887](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/runner/runner.py:887)
- **Replay mode must not start players, run benchmarks, or publish results.** Load `COGAME_LOAD_REPLAY_URI`, detect the profiler format from its bytes/header rather than a URL suffix, and autoplay with looping. [GAME.md:46](/Users/jamesboggs/coding/metta/packages/coworld/src/coworld/docs/roles/GAME.md:46)

## Interpretation

- **Service access does not prove different-node placement.** This measures the actual Service path assigned to the episode; it cannot classify same-node versus cross-node cases without externally joined placement evidence.
- **The earliest Service cold path is partly hidden by the init container.** Successful health hits help bracket readiness, but do not reveal failed DNS attempts, routing propagation, or image pull.
- **A first global message is not a first action.** Preserve independent milestones for first accepted player, first delivered observation, first usable action, and first measured tick.
- **Successful schema validation is not measurement attestation.** Player-reported processing remains self-reported. Use pinned bundled policies for experiments and validate timestamp ordering and correlation IDs.
- **Timing overlap matters.** Parallel slot turns, resource stalls, send waits, and GC intervals are not additive wall time.
- **Timeouts and dropped observations must remain visible.** Percentiles of successful replies alone can improve while service quality worsens.
- **Do not attribute the derived dashboard ratio to `game.step`.** “Avg Running Time per Step” divides aggregate running duration by aggregate episode length; it does not measure step execution. [dashboards.py:1691](/Users/jamesboggs/coding/metta/devops/datadog/dashboards.py:1691)
- **This Coworld does not add Kubernetes spans automatically.** Existing dashboards explicitly identify `player.connect`, `player.turn`, and `game.step` as arena-only. [dashboards.py:6356](/Users/jamesboggs/coding/metta/devops/datadog/dashboards.py:6356)

## Perturbation and data survival

- Buffer compact timing records during the workload; serialize and compress after measurement.
- Keep payload construction, logging, artifact uploads, and clock calibration separately labeled.
- Record instrumentation settings, dependency versions, payload entropy, compression, queue limits, and exact workload counts.
- Treat postmortem artifacts as incomplete after abrupt termination. Neither `atexit` nor a final upload survives every kill.
- For long runs, optionally checkpoint player ZIPs every sixty seconds, with checkpoint intervals explicitly marked. Do not publish partial results as checkpoints.
- Keep raw trace sizes and experiment byte budgets bounded. A 2 MiB observation across sixteen slots is already 32 MiB per tick before protocol overhead.
- Compare repeated episodes with identical image/config/policy inputs. Startup cache state and node load remain confounders; the game cannot prove them away.

All data delivery stays within results, replay, player artifacts, and collected logs. No Datadog, OTLP, new platform environment variables, or worker changes are required. That preserves the agentless boundary and the withdrawn game-contract extension’s scope.
